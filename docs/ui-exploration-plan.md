# UI 探索计划与 Fidelity Ledger

## 目的与证据等级

本文件把已确认的视觉原则、当前代码实现和后续验收证据放在同一账本中。状态含义：

- `implemented`：代码中已实现，并有自动化或静态检查支持。
- `browser-verified`：已在桌面浏览器或桌面视口模拟中观察到。
- `pending-device`：必须在真实设备或真实微信 WebView 中验证，当前没有证据。
- `failed`：已观察到与规格不符，必须附复现信息。

桌面响应式模拟、UA 字符串模拟和 CSS 代码存在都不能替代 `pending-device` 项目的真机证据。

## 已确认的视觉原则

1. 品牌固定为“朗世乐”，整体采用深石墨、去饱和青绿、毛玻璃/半透明、极简与轻立体感。
2. 用户提供的人物是独立背景层；上半身保持清晰，下半身允许被游戏栏、服务入口、底栏和实验抽屉遮挡，以构成真实复杂 Blur 场景。
3. 四种 Glass Mode 共用一套 React/DOM 内容与交互树，只切换表面实现，避免结构差异污染性能对比。
4. 普通玻璃只使用中性边框、内高光、阴影与噪点，不加发光边缘；暖色发光只属于当前选中的游戏、底栏或实验选项。
5. 游戏切换为低高度、细长的四项横栏；只有选中的游戏显示代码绘制的近似图标。
6. 六个服务入口使用不同宽高的非正方形网格，避免等大方块的僵硬感。
7. 底部五项导航固定在 Safe Area 上方；所有交互保持移动触摸目标与可访问名称。
8. Demo 字体为可替换的 `LSVIS TD.woff2`，不构成最终品牌字体决定。

## 真机验收流程

1. 从 Pages URL 进入，记录匿名设备信息与页面 build version。
2. 分别在竖屏与横屏检查非零 Safe Area、横向溢出、底栏和实验面板。
3. 依次查看四种 Glass Mode；保持其他负载设置不变，确认内容与布局没有变化。
4. 检查普通玻璃无边缘发光，当前游戏、底栏和实验选项的暖色焦点清晰但不过曝。
5. 检查人物上半身清晰，下半身被多层玻璃遮挡且文字仍有足够可读性。
6. 验证触摸、滚动、旋转、前后台切换、Reduced Motion 与服务占位层关闭。
7. 运行完整 Benchmark，观察 UI 终态为 `completed` 并确认未取消后再导出报告；按[设备模板](./device-test-template.md)保存完成证据。schema 1 JSON 本身不导出 Benchmark status/elapsed。
8. 对比截图时至少覆盖：文案、布局、字体、色彩、玻璃/选中发光、人物裁切、响应式和动态。

## 完成条件

视觉与真机阶段只有在以下条件同时满足后才能标记完成：

- 至少一台具有非零 Safe Area 的真实设备完成竖屏、横屏与旋转验证。
- iOS 或 Android 的真实微信 WebView 至少完成一次前台 Benchmark、记录 UI 终态 `completed` 且未取消、完成一次前后台切换验证和报告操作记录；若只覆盖一个平台，另一平台继续标记 pending。
- 每个关键截图都有匿名设备代号、日期、方向、页面 build 与对应 ledger 行。
- 所有失败项都有复现步骤；所有不可测指标保留真实状态，不用 0 或主观估计替代。
- 结论明确区分代码/自动化证据、桌面浏览器证据与真机证据。

截至当前文档检查点，真实非零 Safe Area 与真实微信 WebView 仍为 **pending-device**。
